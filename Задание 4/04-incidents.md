# 04. Разбор обращений сотрудников

## Краткий ответ

### 1. B2B-сайт: ошибка 500

1. **Причина.** В кеше настроек остался адрес старого сервера базы.
2. **Доказательства.** `env_excerpt.txt:5` — новый адрес; `ls_bootstrap_cache.txt:7` — старый; `laravel.log:2` — отказ подключения к старому серверу.
3. **Сейчас.** Выполнить в приложении `php artisan config:clear` и `php artisan config:cache`; проверить подключение к новой базе, вход и цены. Доступность новой базы ещё нужно подтвердить.
4. **Профилактика.** Автоматически пересобирать кеш настроек и проверять сайт после обновления.
5. **Ответ сотруднику.** «Сайт обращается к прежнему серверу базы. Обновим настройки и проверим его работу».

### 2. Хостинг: ошибка 503

1. **Причина.** Достигнут лимит обработки запросов: EP 20/20. Вероятные источники нагрузки — задачи по расписанию и бот.
2. **Доказательства.** `error.log:1–3` — лимит достигнут; `access.log:28–29` — оформление заказов получает 503; `crontab.txt:2–4` — одновременный запуск задач.
3. **Сейчас.** Ограничить запросы бота к каталогу, разнести задачи по времени; проверить оформление заказа, обновление цен и остатков, отсутствие новых отказов при следующем запуске задач.
4. **Профилактика.** Ограничить одновременную работу задач; можно добавить мониторинг нагрузки и уведомления.
5. **Ответ сотруднику.** «При высокой нагрузке сайт временно не принимает часть заказов. Снизим нагрузку и проверим оформление».
6. **Уточнить.** По активным процессам во время сбоя проверить вклад бота и каждой задачи: их отдельное влияние пока не доказано.

### 3. Обмен с 1С: заказы не передаются

1. **Причина.** Заказ `ORD-B2B-7781` отклоняется с сообщением «Контрагент не найден» и блокирует следующие задания.
2. **Доказательства.** `exchange.log:4–7` — ошибка и остановка обработки; `queue_snapshot.txt:5–12` — 190 попыток у первого заказа, ни одной у следующих семи.
3. **Сейчас.** Проверить наличие и связь клиента `K-117` в 1С, исправить данные и повторить отправку; сверить все восемь заказов с документами 1С, исключить дубли.
4. **Профилактика.** Откладывать заказы с ошибками данных, продолжать независимые задания; ограничить повторы и уведомлять о задержках.
5. **Ответ сотруднику.** «Передача остановилась на заказе с нераспознанным клиентом. Проверим его данные и восстановим отправку остальных заказов».

### 4. Магазин: продажи не появились в 1С

1. **Причина.** На кассе сбилась дата; модуль пропустил продажи с датой 01.01.2026 как относящиеся к закрытому периоду.
2. **Доказательства.** `pos_sync.log:3–6` — неверная дата, слабая батарейка часов, нет синхронизации; `exchange_retail.log:3–5` — получено 143 чека, создано 0, пропущено 143.
3. **Сейчас.** Сохранить выгрузку, восстановить время кассы; подтвердить дату смены по Z-отчёту и согласовать с бухгалтером повторную загрузку. Сверить 143 чека на 4 155,90 BYN, дату 21.10.2026 и отсутствие дублей.
4. **Профилактика.** Настроить синхронизацию времени и проверку батарейки; можно добавить сверку кассы с 1С и уведомления о пропущенных сменах.
5. **Ответ сотруднику.** «Чеки дошли до сервера, но продажи не загрузились из-за неверной даты кассы. Проверим дату смены и восстановим загрузку».

### В каком порядке взяться за обращения

1. **B2B-сайт.** Он полностью недоступен: сначала нужно вернуть людям возможность работать.
2. **Ошибка 503.** Покупатели не могут оформить часть заказов, поэтому бизнес теряет продажи.
3. **Обмен с 1С.** Принятые заказы ждут дальнейшей обработки, и задержка растёт.
4. **Продажи магазина.** Нужно восстановить учёт за прошлый день; передача чеков на сервер подтверждена.

Если касса продолжает ставить неверную дату или данные нужны для срочного закрытия учёта, обращение магазина подниму выше. Приоритеты уточню по текущему влиянию на работу людей и продажи.





## Подробный разбор

### 1. B2B-сайт: ошибка после переноса базы

1. **Причина.** После переноса базы сайт использует старые сохранённые настройки (кеш конфигурации Laravel). Он обращается к прежнему серверу базы и получает отказ в подключении.
2. **Доказательства.** В `logs/inc1-b2b-500/env_excerpt.txt:5` указан новый сервер — `db-new.example.test`. В `ls_bootstrap_cache.txt:6–7` показано, что в кеше остался `db-old.example.test`. В `laravel.log:2–5` сайт обращается к этому старому серверу и получает `Connection refused`. В `deploy.log:7–11` после замены `.env` пересборка кеша не показана.
3. **Что сделать сейчас.** На сервере, в каталоге работающего приложения и под его пользователем, выполнить `php artisan config:clear`, затем `php artisan config:cache`. Проверить, что приложение использует новый адрес базы, успешно выполняет запрос `SELECT 1`, позволяет войти на сайт и открыть цены. После этих действий проверить отсутствие новых ошибок подключения в логе. Доступность новой базы по предоставленным файлам не подтверждена; если ошибка останется, проверить её доступность с сервера сайта и параметры подключения.
4. **Как избежать повторения.** Добавить в скрипт обновления автоматическую пересборку кеша настроек после замены `.env`, до запуска миграций. Автоматически проверять подключение к новой базе и загрузку страницы сайта с данными из неё. При ошибке останавливать обновление и уведомлять ответственного; отмечать успех только после прохождения проверок. Дополнительно можно настроить круглосуточный мониторинг сайта и подключения к базе с уведомлениями о сбоях. Плюсы: раннее обнаружение проблем, меньше ручных проверок. Минусы: затраты на настройку и поддержку, возможны ложные тревоги.
5. **Ответ сотруднику.** «После переноса сайт продолжает обращаться к прежнему серверу базы данных. Обновим настройки подключения и проверим вход на сайт и отображение цен».

### 2. Хостинг: сайт периодически выдаёт 503

1. **Причина.** Во время сбоев сайт достигает лимита хостинга: заняты все 20 разрешённых мест обработки запросов (EP), поэтому часть новых запросов получает отказ. Вероятный источник перегрузки — одновременная работа задач по расписанию и бота, обходящего каталог. Вклад каждого источника ещё нужно проверить.
2. **Доказательства.** В `logs/inc2-hosting-503/error.log:1–3` указано `Entry processes limit (EP) 20/20`; в `access.log:27–29` в те же секунды зафиксированы ответы 503, в том числе при оформлении заказа (`POST /checkout`). В `lve_usage.csv:5–9,12–14` достижение лимита и отказы совпадают со сбоями в 09:00–09:03 и 09:15–09:16, после чего показатели снижаются. В `crontab.txt:2–4` цены и остатки обновляются одновременно каждые 15 минут, а в 09:00 запускается ещё и пересборка каталога. В `access.log:23–26,127–130` видны эти задачи и медленные запросы бота `203.0.113.77`; задачи выполняются 58, 41 и 240 секунд. Память в предоставленных замерах не достигает лимита 2048 МБ.
3. **Что сделать сейчас.** Проверить текущие показатели хостинга и активные задачи. Если перегрузка продолжается, временно ограничить частоту запросов бота `203.0.113.77` к каталогу; если этого недостаточно — временно заблокировать его доступ к каталогу. Перенести тяжёлую пересборку каталога на менее загруженное время, а обновления цен и остатков разнести по времени, сохранив нужную бизнесу частоту. Если быстро снизить нагрузку не удаётся, запросить у хостинга временное увеличение лимитов.
   **Проверка результата.** Наблюдать за следующим запуском задач: EP должен оставаться ниже 20, новые отказы не должны появляться. Проверить каталог и оформление тестового заказа по согласованной процедуре, затем убедиться, что цены и остатки обновились. Для уточнения причины запросить список активных процессов во время пика и время выполнения запросов к базе; менять настройки поэтапно и сравнивать показатели.
4. **Как избежать повторения.** Можно запускать служебные задачи напрямую из командной строки (CLI), чтобы они не занимали обработчики сайта; лимиты CPU и памяти хостинга при этом сохранятся. Другой вариант — очередь задач с ограниченным числом обработчиков, чтобы распределять нагрузку. Можно добавить запрет повторного запуска ещё работающей задачи, ускорить медленные запросы каталога и кешировать результаты с учётом актуальности цен и остатков. Если после оптимизации ресурсов всё равно не хватает — рассмотреть тариф с большими лимитами или отдельный сервер. Выбор требует замеров; недостаточность текущего тарифа для оптимизированного сайта пока не доказана.
   **Дополнительное предложение.** Можно настроить круглосуточный мониторинг доступности сайта, ошибок 503, использования EP и сбоев фоновых задач с уведомлениями. Плюсы: раннее обнаружение перегрузки, меньше ручных проверок. Минусы: затраты на настройку и поддержку, возможны ложные тревоги.
5. **Ответ сотруднику.** «В моменты высокой нагрузки сайт достигает ограничения хостинга, поэтому часть заказов не удаётся оформить. Снизим нагрузку и проверим оформление заказа и обновление цен и остатков».

### 3. Обмен с 1С: заказы остаются в очереди

1. **Причина.** Заказ `ORD-B2B-7781` не принимается: сервис обмена отвечает «Контрагент не найден» для клиента `K-117`, УНП `190000000`. Контрагент — клиент или организация, на которых оформляется документ в 1С. После этой ошибки программа прекращает обработку и каждую минуту повторяет тот же заказ, поэтому следующие заказы остаются без отправки. Почему контрагент не найден — его нет в 1С, неверны реквизиты или связь с клиентом сайта — по имеющимся данным не установлено.
2. **Доказательства.** В `logs/inc3-exchange-1c/exchange.log:2–3` два предыдущих заказа переданы успешно, с номерами документов 1С. В `exchange.log:4–7` видны ответ `HTTP 422`, сообщение «Контрагент не найден», остановка обработки (`worker stopped batch on error`) и повторная попытка через минуту. В `exchange.log:382–383` число попыток достигает 190, а очередь — восьми заказов. В `queue_snapshot.txt:5–12` у проблемного заказа 190 попыток, у следующих семи — ни одной. В `queue_snapshot.txt:27` клиент `K-117` создан на сайте в 07:51:10; наличие соответствующего контрагента в 1С этим не подтверждается.
3. **Что сделать сейчас.** Найти контрагента в 1С по УНП и сверить его с клиентом `K-117` и данными отправляемого заказа. Если запись есть — исправить связь или неверные реквизиты; если её нет — согласовать создание и выполнить его штатным способом. Саму конфигурацию 1С не менять. Перед повторной отправкой проверить, не создан ли документ по номеру заказа ранее, чтобы избежать дубля. После исправления повторить отправку проблемного заказа и проверить продвижение очереди.
   **Если исправление задерживается.** При наличии штатной возможности временно отложить только проблемное задание и продолжить обработку независимых заказов. Сохранить его данные и ошибку для последующего исправления; не удалять задание и не отмечать его выполненным без подтверждения из 1С. Если такой возможности нет, сначала исправить данные клиента либо доработать модуль обмена.
   **Проверка результата.** Для всех восьми задержанных заказов сверить номера, состав, суммы и клиентов с документами в 1С. Проверить отсутствие дублей, успешные ответы в журнале и уменьшение очереди. Убедиться, что следующий новый заказ тоже передаётся. Если связь с контрагентом остаётся неясной, запросить правила сопоставления клиентов и журнал сервиса на стороне 1С.
4. **Как избежать повторения — предложения.** В модуле обмена можно отдельно обрабатывать ошибки данных: откладывать такой заказ до исправления, уведомлять ответственного и продолжать независимые задания. Временные сбои связи можно повторять с увеличением интервала и ограничением числа попыток. Стоит проверять связь клиента с контрагентом до отправки заказа и обеспечить защиту от дублей по постоянному идентификатору заказа (идемпотентность). Эти изменения относятся к модулю обмена, а не к конфигурации 1С.
   **Дополнительное предложение.** Можно автоматически отслеживать количество и возраст ожидающих заказов, повторные ошибки и время последней успешной передачи. Плюсы: зависание обмена обнаружится до обращения бухгалтера. Минусы: потребуется настроить пороги уведомлений и назначить ответственного за исправление ошибок.
5. **Ответ сотруднику.** «Передача остановилась на заказе, для которого не удалось найти клиента в 1С; следующие заказы ожидают отправки. Проверим данные клиента, восстановим передачу и сверим задержанные заказы с документами в 1С».

### 4. Розничный магазин: продажи за день не появились в 1С

1. **Причина.** После перезапуска кассы POS-02 её дата оказалась 01.01.2026: в журнале есть предупреждение о слабой батарейке часов и отсутствии настроенной синхронизации времени. По обращению, в это утро отключали электричество. Смена №1188 записана в журнале с неверной датой. Сервер обмена получил все 143 чека, но модуль пропустил их: выбранная дата документа 01.01.2026 находится раньше границы закрытого периода 1С — 01.10.2026. Поэтому документ «Отчёт о розничных продажах» не создан. Даты непосредственно в фискальных чеках по этим логам не установлены.
2. **Доказательства.** В `logs/inc4-retail-pos/pos_sync.log:3–6` видны `RTC battery low`, `system time not synchronized (ntp: no server configured)`, открытие и закрытие смены №1188 с датой 01.01.2026 и отправка 143 чеков с ответом `200 OK`; сумма смены — 4 155,90 BYN. В `exchange_retail.log:3` сервер принимает эту смену 21.10.2026 в 21:03:15. В строках 4–5 прямо указаны причина пропуска и итог: `created=0 skipped=143 errors=0`. Значит, успешная передача и отсутствие ошибок в итоговом счётчике не означают, что продажи загружены в 1С.
3. **Что сделать сейчас.** Сохранить исходную выгрузку чеков, журналы и Z-отчёт. Проверить текущие дату, время и часовой пояс кассы; выяснить, не затронуты ли следующие смены. Согласовать с ответственным за кассу восстановление правильного времени по инструкции кассовой системы, настроить сервер точного времени (NTP) и проверить синхронизацию. Заменить слабую батарейку часов при обслуживании. Простое исправление часов не исправит уже выгруженные данные.
   **Как восстановить продажи.** По Z-отчёту и данным кассовой системы подтвердить, что смена №1188 относится к 21.10.2026. Совместно с бухгалтером определить штатный способ загрузки с верной датой: повторную выгрузку, если она корректно формирует дату документа, либо исправление даты импортируемого документа средствами модуля обмена. Исходные и фискальные чеки не переписывать, закрытый период ради загрузки ошибочной даты не открывать. Перед повторной обработкой проверить, не создан ли документ по магазину №2 и смене №1188, и обеспечить защиту от дублей. Если штатный способ неизвестен, запросить описание формата выгрузки, правила выбора даты документа и инструкцию повторной обработки пропущенных смен.
   **Проверка результата.** В 1С за 21.10.2026 должен появиться один отчёт по магазину №2 и смене №1188: 143 чека, сумма 4 155,90 BYN. Сверить его с Z-отчётом и исходной выгрузкой, проверить отсутствие дублей и необработанных чеков. Проверить правильность времени кассы и дату следующей выгружаемой смены.
4. **Как избежать повторения — предложения.** Можно настроить автоматическую синхронизацию времени и проверку даты кассы при запуске; при большом расхождении уведомлять ответственного и действовать по инструкции кассовой системы. В обслуживание оборудования стоит включить проверку батарейки часов. В модуле обмена можно сохранять пропущенные смены для разбора и повторной обработки, а результат с пропущенными чеками отмечать как требующий внимания, даже если `errors=0`.
   **Дополнительное предложение.** Можно автоматически сверять по каждому магазину и смене количество чеков и сумму между кассой, сервером обмена и 1С. При расхождении или отсутствии отчёта после ожидаемого времени загрузки отправлять уведомление. Плюсы: обнаруживаются пропуски даже при успешном ответе сервера. Минусы: потребуется связать данные трёх систем и учитывать задержки загрузки и согласованные исключения.
5. **Ответ сотруднику.** «Чеки дошли до сервера, но из-за неверной даты на кассе продажи не загрузились в 1С. Проверим дату смены по Z-отчёту, восстановим загрузку без дублей и исправим настройку времени кассы».

### Порядок обработки, если обращения поступили одновременно

Сначала уточню, какие сбои продолжаются сейчас и сколько пользователей затронуто. При описанном масштабе порядок такой:

1. **B2B-сайт, ошибка 500.** Сайт полностью недоступен для его пользователей; нужно восстановить доступ. Причина подтверждается файлами, есть конкретное действие для исправления.
2. **Хостинг, ошибка 503.** Часть покупателей не может оформить заказ. Нужно снизить нагрузку и проверить восстановление оформления заказов.
3. **Обмен заказами с 1С.** Задержка затрагивает все следующие задания очереди и растёт; нужно исправить проблемного клиента или безопасно отложить его заказ, чтобы продолжить обработку независимых заказов.
4. **Продажи магазина №2.** По обращению отсутствуют данные за прошлый день, а сервер обмена подтвердил приём чеков. Нужно сохранить исходные данные и восстановить учёт. Если касса и сейчас ставит неверную дату, продолжают появляться ошибочные смены либо приближается срок закрытия учёта, приоритет этого обращения повышу.

## Команды, использованные при анализе

Логи читались в PowerShell с выводом имени файла и номера строки. Пример для четвёртого обращения; для остальных использовался тот же способ с соответствующим путём. Запуск из папки `tasks/04-support-incidents`:

```powershell
$incidentPath = 'logs/inc4-retail-pos'
Get-ChildItem -LiteralPath $incidentPath -File | ForEach-Object {
    $incidentFile = $_
    $incidentLine = 0
    Get-Content -LiteralPath $incidentFile.FullName -Encoding UTF8 | ForEach-Object {
        $incidentLine++
        '{0}:{1}: {2}' -f $incidentFile.Name, $incidentLine, $_
    }
}
```

Для сопоставления запусков задач и периодов восстановления во втором обращении использовался поиск:

```powershell
$incidentPath = 'logs/inc2-hosting-503'
rg -n '/cron/|09:04:|09:15:00|09:17:' "$incidentPath\access.log"
```
